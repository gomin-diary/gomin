# 커밋 메시지 작성 규칙

커밋 메시지는 변경 목적을 한눈에 알 수 있도록 작성한다. 제목은 다음 형식을 사용한다.

```text
<type>: <메시지>
```

타입은 영문 소문자로 쓰고, 콜론 뒤에는 공백을 하나 넣는다. 메시지는 한국어로 작성하되 코드 식별자와 기술 이름은 그대로 쓴다.

## 타입

| 타입 | 사용 기준 | 예시 |
| --- | --- | --- |
| `feat` | 새로운 기능 추가 | `feat: 일기 목록 조회 기능 추가` |
| `fix` | 잘못된 동작이나 오류 수정 | `fix: 일기 목록의 날짜 정렬 오류 수정` |
| `refactor` | 외부 동작을 유지하면서 코드 구조 개선 | `refactor: 일기 조회 로직을 서비스로 분리` |
| `docs` | 문서 추가·수정·이동 | `docs: 커밋 메시지 작성 규칙 추가` |
| `test` | 테스트 추가·수정 | `test: 개발 서버 종료 테스트 추가` |
| `style` | 동작에 영향을 주지 않는 코드 서식 수정 | `style: API 모듈의 들여쓰기 정리` |
| `perf` | 성능 개선 | `perf: 일기 목록의 중복 조회 제거` |
| `build` | 빌드 설정이나 의존성 변경 | `build: Next.js 의존성 버전 업데이트` |
| `ci` | CI/CD 작업과 자동화 설정 변경 | `ci: 프론트엔드 타입 검사 단계 추가` |
| `chore` | 다른 타입에 해당하지 않는 유지보수 | `chore: 로컬 디자인 폴더를 Git 추적 대상에서 제외` |
| `revert` | 이전 커밋의 변경 취소 | `revert: 일기 목록 캐시 적용 취소` |

예시는 메시지 작성 방식을 보여주기 위한 것이며, 해당 기능의 구현 여부를 뜻하지 않는다.

## 작성 기준

- 변경 대상과 내용을 구체적으로 쓴다. `fix: 오류 수정`보다 `fix: 빈 일기 목록에서 발생하는 오류 수정`처럼 작성한다.
- `추가`, `수정`, `제거`, `분리` 등 변경을 설명하는 말로 끝내고, 제목 끝에는 마침표를 붙이지 않는다.
- 작업 과정이나 완료 소감 대신 최종 변경 내용을 적는다. `작업 완료`, `수정 중`, `다시 수정`처럼 내용이 드러나지 않는 표현은 피한다.
- 한 커밋에는 하나의 목적을 담는다. 서로 관련 없는 변경은 커밋을 나눈다.
- 타입은 변경 목적을 기준으로 고른다. 오류를 고치면서 코드를 정리했다면 `fix`, 동작 변경 없이 구조만 정리했다면 `refactor`를 사용한다.
- 화면 배치나 디자인 변경은 코드 서식 변경인 `style`과 구분한다. 새로운 UI는 `feat`, 잘못된 표시 수정은 `fix`를 사용한다.
- `docs`, `test`, `build`, `ci`처럼 맞는 타입이 있으면 `chore`보다 우선한다.

## 본문

제목만으로 충분하면 본문은 생략한다. 변경 이유나 영향, 검증 결과를 설명해야 할 때는 제목 다음에 빈 줄을 두고 작성한다. 검증 결과는 실제로 확인한 내용만 적는다.

```text
fix: 빈 일기 목록에서 발생하는 오류 수정

조회 결과가 없을 때 첫 번째 항목에 접근하던 로직을 수정한다.
빈 목록에서는 안내 문구를 표시한다.

검증: 빈 목록과 항목이 있는 목록의 렌더링 테스트 통과
```
