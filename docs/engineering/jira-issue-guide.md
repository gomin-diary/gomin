# Jira 이슈 유형과 작업 분해 기준

사람과 AI가 GOMIN의 업무를 같은 기준으로 분류하기 위한 지침입니다. 이슈 유형은 파일 수나 작업 기간보다 **무엇을 관리하려는지**를 기준으로 선택합니다.

## 1. 유형별 의미

| 유형 | 의미 | 판단 질문 | 완료 기준의 초점 |
| --- | --- | --- | --- |
| Epic | 큰 업무 영역 안에서 여러 Story/Task를 묶는 목표 | 여러 독립 결과가 모여 어떤 목표를 달성하는가? | 범위에 포함된 결과와 전체 목표 달성 |
| Story | 사용자나 개발자가 얻게 되는 결과 | 누가 무엇을 할 수 있게 되는가? | 관찰·검증할 수 있는 사용 결과 |
| Task | 기술적 또는 운영적인 독립 작업 | 무엇을 수행해야 하는가? | 작업 산출물이나 운영 상태 |
| Sub-task | Story/Task를 완료하기 위한 세부 작업 | 부모의 어떤 완료 기준을 충족하는가? | 부모 범위 안의 구체적인 기여 |

- Epic은 단순한 분류 폴더가 아닙니다. 달성할 목표와 완료 범위를 명시합니다.
- Story의 사용자는 최종 사용자뿐 아니라 개발자·운영자일 수도 있습니다.
- Task도 사용자에게 가치를 줄 수 있습니다. 가치가 있다는 이유만으로 모두 Story가 되는 것은 아닙니다.
- Sub-task는 부모 없이 별도로 관리할 의미가 약한 작업입니다. 단순히 작다는 이유로 선택하지 않습니다.

## 2. 관계와 크기

```text
Epic
├─ Story
│  └─ Sub-task (필요할 때만)
└─ Task
   └─ Sub-task (필요할 때만)
```

Story와 Task는 같은 계층입니다. `Epic → Story → Task → Sub-task`처럼 네 단계로 만들지 않습니다. Story의 구현을 나누려면 Sub-task를 사용합니다. 별도 목표와 완료 기준이 있는 독립 Task라면 Epic 아래에 두고 필요에 따라 의존 관계를 연결합니다.

모든 유형을 사용할 필요는 없습니다. 독립적인 기술 작업만 있다면 `Epic → Task`로 충분합니다. 별도 담당, 검증 또는 진행 추적이 필요하지 않은 세부사항은 Description의 체크리스트로 남깁니다. 커밋 하나, 파일 하나, 패키지 하나를 자동으로 이슈 하나로 변환하지 않습니다.

## 3. Story와 Task 선택 순서

1. 먼저 이슈의 목적과 완료 기준을 한두 문장으로 작성합니다.
2. 여러 독립 결과를 묶는 목표라면 Epic을 선택합니다.
3. 특정 부모의 일부이고 독립성이 약하면 Sub-task 또는 부모의 체크리스트로 둡니다.
4. 특정 사용자가 수행할 수 있는 행동을 중심으로 검증한다면 Story를 선택합니다.
5. 기술적 산출물이나 운영 작업의 수행 여부를 중심으로 검증한다면 Task를 선택합니다.

제목만 바꿔 유형을 결정하지 않습니다. 예를 들어 “개발자로서 패키지를 설치하고 싶다”는 표현만으로 의존성 설치 작업이 Story가 되지는 않습니다. 두 유형이 모두 가능하면 실제 완료 기준과 기존 이슈의 목적에 맞는 하나를 선택하고 동일한 범위를 중복 생성하지 않습니다.

| 구분 | Story로 정의하는 경우 | Task로 정의하는 경우 |
| --- | --- | --- |
| 로컬 개발환경 | 개발자가 한 명령으로 앱을 실행하고 대상별 재시작을 할 수 있다 | 공통 설치 및 실행환경을 구성한다 |
| 데이터베이스 연결 | 개발자가 상태 API로 DB 연결 성공과 실패를 확인할 수 있다 | Supabase SDK·설정·상태 확인 RPC를 구성한다 |
| 배포 | 운영자가 변경을 배포하고 서비스 응답을 확인할 수 있다 | Frontend CI/CD 및 Vercel 배포를 구성한다 |

위 각 행은 같은 영역을 표현하는 대안입니다. 양쪽을 모두 생성하라는 뜻은 아닙니다. Story로 관리할 때는 실제 실행·관찰 결과를 완료 기준으로 삼고, 구성 파일의 존재만으로 완료를 판단하지 않습니다.

## 4. 개발환경 구축 분류 예시

| 작업 | 유형 | 분류 기준 |
| --- | --- | --- |
| 개발 환경 구축 | Epic | 프로젝트 기반·실행·DB 연결·배포를 묶는 목표이므로 적절합니다. |
| 프로젝트 기본 개발환경 구성 | Task | 구조와 버전·의존성 관리라는 독립 기술 작업입니다. |
| Next.js / TypeScript Frontend 개발환경 구성 | Task | 앱·상태관리·API 호출 기반의 구성 결과를 관리합니다. |
| FastAPI Backend 개발환경 구성 | Task | 서버 실행·설정·상태 API 기반의 구성 결과를 관리합니다. |
| Supabase 로컬·Cloud 개발환경 및 Backend 연결 구성 | Task | DB 환경과 연결 구성을 하나의 기술 결과로 관리합니다. 개발자의 연결 확인 경험을 중심으로 새 범위를 정의한다면 Story 표현도 가능합니다. |
| Frontend / Backend 통합 개발 실행환경 구성 | Task | 실행환경 구축이라는 기술 작업으로 적절합니다. 처음부터 개발자의 실행·재시작 경험을 중심으로 계획한다면 Story로 정의할 수도 있습니다. |
| Frontend CI/CD 및 Vercel 배포 구성 | Task | 독립적인 배포·운영 기반 구성입니다. |
| Backend CI/CD 및 Render 배포 구성 | Task | 독립적인 배포·운영 기반 구성입니다. |
| 개발환경 실행 및 설정 문서화 | Task | 여러 개발환경 결과를 설명하는 문서 산출물과 정합성을 관리합니다. |

## 5. Sub-task를 사용하는 예

```text
Story: 개발자가 공통 명령으로 로컬 앱을 실행하고 재시작할 수 있다
├─ Sub-task: 공통 설치 흐름 구성
├─ Sub-task: 앱 통합 실행 및 대상별 재시작 구성
└─ Sub-task: 설치·재시작·종료 시나리오 검증
```

각 하위 작업을 별도로 추적할 필요가 있을 때만 이렇게 분해합니다. `dev.mjs 작성`, `환경변수 한 개 추가`, `패키지 설치` 같은 구현 세부사항은 보통 부모 Description에 포함합니다. 여러 작업에 걸친 독립적인 문서화는 Task가 될 수 있고, 특정 Story의 안내만 보완한다면 그 Story의 Sub-task 또는 체크리스트로 둘 수 있습니다.

## 6. 이슈 작성 기준

- **제목:** 구현 수단보다 완료 결과를 표현합니다. Story는 가능한 행동, Task는 독립 작업 결과, Sub-task는 부모에 기여하는 세부 결과를 드러냅니다.
- **목적:** 대상 사용자 또는 기술·운영 목적을 적습니다. Epic에는 전체 목표와 포함·제외 범위를 적습니다.
- **내용:** 예정 작업과 이미 완료된 내용을 구분합니다. 역등록이라면 확인된 완료 내용만 적습니다.
- **완료 기준:** 구현 여부나 사용자 행동을 확인할 수 있는 조건을 적습니다. Sub-task는 부모의 어떤 기준을 충족하는지 연결합니다.
- **근거:** 역등록·완료 처리 시 코드 경로, 커밋, 검증 결과 또는 사용자 확인을 구분해 기록합니다. 커밋 메시지만으로 완료를 판단하지 않습니다.
- **날짜:** 기존 날짜 필드와 사용자 요청을 따릅니다. 생성일을 과거로 조작하거나 날짜를 맞추기 위해 작업을 분할하지 않습니다.

## 7. AI의 Jira 작업 절차

1. 요청이 문서 작성인지 실제 Jira 변경인지 구분합니다. 문서화 요청만으로 이슈를 생성·수정하지 않습니다.
2. 실제 Jira 작업 시 프로젝트의 유형, 계층, Parent 필드와 가능한 상태 전환을 조회합니다. 표시 이름만으로 유형을 판별하지 말고 Sub-task 여부와 계층 메타데이터를 확인합니다.
3. 기존 이슈의 제목뿐 아니라 Description, 완료 기준, Parent를 읽어 의미상 중복을 검사합니다. 목적이 같으면 재사용을 우선합니다.
4. 관련 문서, 현재 코드·설정, 로컬 Git 이력과 사용자 확정 정보를 비교합니다. 확인하지 않은 배포 설정이나 검증 결과를 만들어내지 않습니다.
5. 목적·범위·완료 기준을 정한 뒤 유형과 관계를 선택합니다. 작은 작업은 체크리스트로 남기고 필요한 경우에만 Sub-task를 만듭니다.
6. 조사 후에도 중요한 사실이나 재사용 대상이 모호하면 변경 전에 최소한의 질문으로 확인합니다. 이미 확인된 사실이나 단순한 표현 선택은 다시 묻지 않습니다.
7. 완료 처리는 근거를 확인한 Sub-task부터 부모 Story/Task, Epic 순서로 진행합니다. 하위 항목 완료뿐 아니라 부모 자체의 완료 기준도 확인합니다.
8. 상태·Parent·날짜·중복 여부를 재조회하고 실제 이슈 키와 결과를 보고합니다. 비밀정보는 읽거나 Jira에 기록하지 않습니다.
