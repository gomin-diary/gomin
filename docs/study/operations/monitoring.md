# 모니터링과 UptimeRobot

배포가 성공한 뒤에도 서비스에 문제가 생길 수 있다. 서버가 멈추거나 DB 연결이 끊기거나 요청이 평소보다 오래 걸릴 수 있다. 모니터링은 이런 상태를 계속 관찰해 변화를 알아차리는 일이다.

## 로그, 지표, 상태 확인

로그는 “언제 어떤 요청이나 오류가 있었는지”처럼 개별 사건을 기록한다. 지표는 응답 시간이나 오류 횟수처럼 상태를 숫자로 모아 보여준다. 상태 확인 API는 미리 정한 검사를 실행하고 그 결과를 응답한다.

| 확인 방법 | 알 수 있는 내용의 예 |
| --- | --- |
| 로그 | 어떤 요청에서 어떤 종류의 오류가 발생했는지 |
| 지표 | 최근 응답 시간이 늘었는지, 오류 비율이 높아졌는지 |
| 외부 HTTP 검사 | 외부에서 특정 주소에 접속하고 기대한 응답을 받을 수 있는지 |
| DB 상태 API | 앱에서 DB 상태 확인 함수를 호출할 수 있는지 |

로그가 있다고 자동으로 알림이 오는 것은 아니다. 알림을 받으려면 어떤 조건을 누구에게 전달할지도 정한다. 로그에는 비밀번호, 세션 토큰, API 키 같은 비밀정보를 남기지 않는다.

## 가용성과 응답 시간

가용성은 서비스를 사용할 수 있는 정도다. 외부 모니터가 표시하는 가동률은 정해진 대상과 검사 방식으로 관찰한 결과다. 전체 사용자의 모든 기능을 그대로 측정한 값은 아니다.

응답 시간은 요청한 뒤 응답을 받기까지 걸린 시간이다. 네트워크, 서버 처리, DB 대기 등이 영향을 준다. 응답이 왔다는 사실과 사용자가 기다릴 만한 속도인지는 따로 살펴본다.

주기적으로 검사하면 검사 사이에 잠깐 발생한 문제를 놓칠 수 있다. 검사 주기와 실패 판단 조건에 따라 장애를 감지하는 시점도 달라진다.

## UptimeRobot은 무엇을 확인할까

UptimeRobot은 외부에서 웹 주소나 API 등에 요청을 보내 상태를 검사하고 알림을 제공하는 서비스다. HTTP 검사에서는 설정한 조건에 맞는 응답을 받는지 확인한다. API 모니터는 상태 코드 외에 JSON 본문이나 헤더의 값도 검사할 수 있다.

따라서 무엇을 정상으로 볼지 정하는 일이 중요하다. 페이지 주소를 검사하는 것과 DB 확인 API를 검사하는 것은 범위가 다르다. 화면의 로그인·입력·저장 과정을 모두 자동으로 검증하려면 그 흐름을 다루는 별도의 검사가 필요하다.

검사 기능에 관한 자세한 내용은 [UptimeRobot 공식 안내](https://help.uptimerobot.com/en/articles/13628553-uptimerobot-api-monitoring)에서 확인한다. 검사 주기와 알림 채널은 각 모니터의 설정에서 확인한다.

## 우리 프로젝트의 상태 확인 API

| 대상 | 현재 코드가 확인하는 범위 | 이것만으로 확인하지 못하는 내용 |
| --- | --- | --- |
| 프론트의 홈 URL에 대한 HTTP 검사 | 해당 주소의 HTTP 응답 여부 | 브라우저의 JavaScript 실행, 인증 API·DB 연결, 로그인 성공 |
| `GET /api/v1/health` | FastAPI의 상태 응답 처리 | DB·Storage·메일 발송 |
| `GET /api/v1/health/db` | Supabase Data API로 `health_check` 함수 호출, 결과가 `true`인지 확인 | 모든 테이블·업무 함수·Storage·메일 발송의 정상 동작 |

DB 상태 확인에 성공하면 HTTP `200`과 다음 데이터를 반환한다.

```json
{
  "success": true,
  "data": { "status": "ok", "database": "connected" },
  "error": null
}
```

호출에 실패하거나 기대한 결과를 받지 못하면 `503`을 반환한다. 이 응답은 DB 확인 과정에 문제가 있다는 신호다. 원인이 Supabase 전체 장애인지, 함수·권한·설정 문제인지는 추가 확인이 필요하다.

홈에 접속한 브라우저는 별도로 인증 API를 호출한다. 외부에서 홈 URL의 HTTP 응답만 검사하는 방식은 이 브라우저 동작까지 실행하지 않는다.

상태 API는 [health.py](../../../backend/app/api/routes/health.py)에 구현되어 있다. 우리 프로젝트는 운영 백엔드의 `/api/v1/health`를 5분마다 확인하고 이메일로 알림을 받는다. 실제 호스트와 알림 연락처 등은 UptimeRobot 대시보드에서 관리한다.

## 알림을 받았을 때 읽는 순서

우선 어느 주소에서 언제부터 어떤 조건이 실패했는지 본다. 같은 시간의 배포·재시작 기록과 로그를 대조하고 프론트·API·DB 중 어느 구간까지 응답하는지 확인한다.

한 번의 검사 실패가 계속되는 장애인지도 살펴본다. 반대로 상태 확인 API가 정상이더라도 특정 사용자나 기능에 오류가 있을 수 있다. 검사 범위를 이해하면 정상 신호를 과하게 해석하거나 오류 원인을 성급하게 단정하는 일을 줄일 수 있다.
