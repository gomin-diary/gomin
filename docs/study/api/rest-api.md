# REST API

API가 프로그램 사이의 사용 약속이라면 REST는 그 약속과 통신 구조를 설계하는 방식이다. Roy Fielding이 웹의 설계를 설명하면서 정리한 아키텍처 스타일이다.

REST API를 처음 접할 때는 리소스와 HTTP 메서드부터 보면 이해하기 쉽다. 다만 주소를 명사로 짓고 JSON을 반환하는 것만으로 REST의 모든 조건을 만족하지는 않는다.

## 리소스와 표현

리소스는 API가 다루는 대상이다. 회원 한 명, 게시글 한 편, 게시글 목록 등이 리소스가 될 수 있다. URI는 그 대상을 식별한다. 웹 API에서 자주 보는 URL도 URI의 한 종류다.

서버는 리소스 자체를 통째로 보내기보다 그 내용을 표현한 데이터를 반환한다. 게시글을 JSON으로 반환했다면 그 JSON이 리소스의 표현이다. 같은 대상을 HTML 등 다른 형식으로 표현할 수도 있다.

다음은 게시글 API의 예시다.

| 요청 | 의도 |
| --- | --- |
| `GET /articles` | 게시글 목록 조회 |
| `GET /articles/42` | 42번 게시글 조회 |
| `POST /articles` | 목록에 새 게시글 생성 요청 |
| `PUT /articles/42` | 42번 게시글의 표현을 요청 내용으로 교체 |
| `PATCH /articles/42` | 42번 게시글의 일부 변경 요청 |
| `DELETE /articles/42` | 42번 게시글 삭제 요청 |

같은 주소를 사용해도 메서드가 다르면 요청의 의미가 달라진다. CRUD는 생성·조회·수정·삭제를 묶어 부르는 말이며 HTTP 메서드와 자주 연결해서 설명한다. 실제 메서드의 의미는 CRUD 네 가지보다 넓다.

## GET, POST, PUT, PATCH를 구분하는 기준

`GET`은 조회를 위한 메서드다. 호출자가 서버의 업무 데이터를 바꾸려고 사용하는 방식으로 설계하지 않는다. 조회 과정에서 접근 로그가 쌓이는 것까지 금지한다는 뜻은 아니다. 이 성질을 안전성이라고 한다.

`PUT`과 `DELETE`는 같은 요청을 여러 번 보내도 의도한 최종 효과가 한 번 보낸 경우와 같다. 이를 멱등성이라고 한다. 이미 지운 대상을 다시 삭제했을 때 응답 코드까지 같아야 하는 것은 아니다.

`POST`는 대상 리소스가 요청 내용을 처리하도록 한다. 새 데이터 생성에 많이 쓰지만 로그인이나 다른 동작에도 사용할 수 있다. 일반적으로 멱등성을 보장하지 않으므로 재시도하면 같은 데이터가 두 번 만들어질 수 있다.

`PUT`은 대상의 표현 전체를 교체하려는 요청이고 `PATCH`는 변경 내용을 전달하는 요청이다. `PATCH`의 멱등성은 변경 방식에 따라 달라진다. “제목을 A로 설정”과 “조회 수를 1 증가”는 반복했을 때 효과가 다르다.

## REST의 기본 원칙

REST는 다음 여섯 가지 제약을 바탕으로 한다.

| 원칙 | 뜻 |
| --- | --- |
| 클라이언트·서버 분리 | 사용자와 상호작용하는 쪽과 데이터를 처리하는 쪽의 책임을 나눈다. |
| 무상태 통신 | 각 요청에 처리에 필요한 정보를 담고 서버에 남긴 이전 대화 상태에 기대지 않는다. |
| 캐시 | 응답을 재사용할 수 있는지 알려 불필요한 통신을 줄인다. |
| 일관된 인터페이스 | 리소스 식별, 표현, 메시지 해석 규칙 등을 일관되게 사용한다. |
| 계층 구조 | 중간의 프록시나 게이트웨이가 있어도 호출자가 내부 구성을 모두 알 필요가 없다. |
| 필요 시 코드 전송 | 클라이언트가 실행할 코드를 보낼 수 있다. 이 제약은 선택 사항이다. |

무상태는 서버에 데이터를 저장하지 않는다는 뜻이 아니다. 회원이나 게시글 같은 리소스 상태는 저장할 수 있다. 구분할 대상은 이전 요청에서 이어지는 클라이언트의 대화 상태다.

더 깊게 보면 일관된 인터페이스에는 응답 안의 링크 등을 따라 다음 행동을 선택하는 원칙도 포함된다. 이를 하이퍼미디어라고 한다. 실무에서는 이 조건을 일부만 적용한 HTTP JSON API도 REST API라고 부른다. 이름만 보고 모든 제약을 만족한다고 판단하지 않는다.

## 우리 프로젝트에서는

현재 API에는 `GET /api/v1/auth/me`, `POST /api/v1/auth/login`, `POST /api/v1/auth/logout` 같은 경로가 있다. 리소스 조회와 로그인·로그아웃 동작이 함께 있다. 엄격한 REST의 예제로 단정하기보다 실제 HTTP API의 설계 사례로 읽으면 된다.

인증은 서버에 저장한 세션을 사용한다. 이 구조는 REST의 무상태 원칙과 구분해서 이해한다. 경로의 `/v1`은 API 버전을 나타내는 프로젝트의 선택이며 REST가 요구하는 고정 형식은 아니다.

오류 응답도 약속의 일부다. 우리 API는 HTTP 오류 상태와 JSON 오류 코드를 함께 반환한다. “요청에 답했다”는 이유로 실패를 모두 HTTP `200`으로 표현하지 않는다.
