# 배포의 기본 개념

내 컴퓨터에서 실행한 웹 서비스를 다른 사람이 사용하게 하려면 외부에서 접근할 수 있는 환경에 프로그램과 설정을 준비해야 한다. 이 과정을 배포라고 부른다. 코드를 저장소에 올리는 일과 사용자가 새 버전을 사용하는 일 사이에는 여러 단계가 있다.

## 로컬, 검증, 운영 환경

로컬 환경은 개발자의 컴퓨터에서 실행하는 환경이다. 검증 환경은 변경 내용을 확인하는 별도 환경이며 운영 환경은 실제 사용자가 접속하는 환경이다. 서비스에 따라 검증용 배포를 프리뷰나 스테이징이라고 부르기도 한다.

같은 코드도 실행 환경에 따라 API 주소, DB, 쿠키 설정 등이 달라진다. 로컬에서 성공했다고 운영에서도 모든 연결이 맞는 것은 아니다. 운영 데이터와 개발용 데이터를 나누는 이유도 이 차이에 있다.

## 의존성 설치, 빌드, 실행

의존성은 프로그램이 사용하는 다른 라이브러리다. 배포 환경은 의존성 목록에 맞춰 필요한 패키지를 설치한다. 잠금 파일은 설치 버전을 일정하게 재현하도록 돕는다.

빌드는 소스 코드를 배포할 결과물로 준비하는 일이다. Next.js는 화면 코드와 정적 페이지 등을 빌드한다. 실행은 준비한 프로그램을 실제 요청에 응답하도록 동작시키는 일이다.

| 단계 | 우리 프로젝트의 예 |
| --- | --- |
| 프론트 의존성 설치 | npm으로 `frontend`의 패키지 설치 |
| 프론트 빌드 | `next build` 전에 문서 데이터를 생성하고 앱 빌드 |
| 백엔드 의존성 설치 | `backend/requirements.txt`의 Python 패키지 설치 |
| 백엔드 실행 | Uvicorn으로 FastAPI 앱 시작 |
| DB 변경 적용 | SQL 마이그레이션을 해당 DB에 적용 |

모든 기술이 같은 빌드 과정을 거치지는 않는다. Python 백엔드의 패키지 설치와 서버 실행은 프론트의 빌드와 구분해서 보면 된다.

## 환경변수

환경변수는 실행 환경이 프로그램에 전달하는 이름과 값이다. 코드에 특정 서버 주소나 비밀값을 고정하는 대신 환경별로 설정하도록 사용한다.

환경변수라는 형식 자체가 비밀을 보장하지는 않는다. Next.js의 `NEXT_PUBLIC_` 변수는 브라우저 코드에 포함될 수 있는 공개 값이다. 특히 이 값은 보통 빌드할 때 반영되므로 배포 설정을 바꾼 뒤 새 빌드가 필요하다.

우리 프론트의 `NEXT_PUBLIC_API_BASE_URL`은 호출할 API의 주소다. 백엔드의 `SUPABASE_SECRET_KEY`는 서버 전용 인증 정보다. 둘을 같은 공개 범위로 취급하지 않는다. 설정 항목은 예제 환경 파일과 [환경변수 안내](../../local-development/environment.md)에서 확인하고 실제 비밀값은 문서에 기록하지 않는다.

## 도메인, DNS, HTTPS

도메인은 사람이 기억하기 쉬운 이름이다. DNS 설정으로 도메인이 어느 서비스에 연결되는지 정한다. 배포 플랫폼에 도메인을 등록하는 일과 DNS 제공자에 연결 레코드를 설정하는 일이 함께 필요할 수 있다.

HTTPS를 사용하려면 해당 도메인의 인증서와 TLS 연결도 준비한다. 호스팅 플랫폼이 인증서를 관리해 주기도 한다. DNS 변경은 캐시 때문에 보는 위치에 따라 반영 시점이 다를 수 있다.

프론트와 API의 주소는 쿠키·CORS 설정에도 영향을 준다. 주소를 바꿀 때는 연결할 도메인만 수정하는 것으로 끝나지 않을 수 있다.

## 자동 검사와 자동 배포

CI는 코드를 합칠 때 테스트·빌드 등을 자동으로 검사하는 흐름을 뜻한다. CD는 배포할 결과물을 준비하거나 실제 배포까지 이어가는 흐름을 가리킨다. 저장소에 코드를 올렸다는 사실만으로 어떤 자동화가 실행됐는지는 알 수 없다.

검사가 통과한 버전과 실제 배포한 버전도 일치하는지 확인한다. 배포가 실패하면 기존 버전이 계속 서비스될 수 있으므로 사용자 화면과 배포 기록을 함께 살펴본다.

## 우리 프로젝트에서는

Next.js는 Vercel, FastAPI·Uvicorn은 Render에서 제공한다. DB와 Storage는 Supabase를 사용한다. 서비스별 자동 배포 대상과 실행 조건은 실제 프로젝트 설정에서 확인한다.

DB 변경이 필요한 배포는 마이그레이션 적용과 앱 배포의 순서를 맞춘다. 우리 운영 절차는 미적용 마이그레이션을 먼저 적용하고 확인한 뒤 Render 백엔드를 배포한다. 백엔드를 시작할 때 운영 DB 구조를 자동으로 바꾸지는 않는다.

이전 코드로 되돌리는 것과 DB 변경을 되돌리는 것도 별개다. 코드 롤백만으로 삭제된 데이터를 복구할 수는 없다. 구체적인 변경·복구 절차는 [Supabase 마이그레이션 관리](../../engineering/database-migrations.md)를 따른다.
