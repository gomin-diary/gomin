# 파일 저장소와 Supabase Storage

서비스에서 이미지를 보관할 때는 파일 내용과 파일에 관한 정보를 함께 관리한다. 이미지의 실제 바이트는 파일 저장소에 두고 소유자나 저장 경로 같은 정보는 DB에 둘 수 있다.

## DB와 파일 저장소를 나누는 이유

DB는 구조화된 데이터를 조건으로 찾고 관계를 관리하는 데 사용한다. 파일 저장소는 이미지, 음성, PDF 같은 파일을 저장하고 전달하는 데 사용한다.

예를 들어 프로필 사진 기능을 설계한다면 파일 저장소에는 사진을, DB에는 회원 식별자와 사진 경로를 저장할 수 있다.

DB에 파일 바이트를 저장하는 방법도 있다. 저장 방식은 파일 크기, 조회 방식, 권한, 운영 비용 등을 보고 결정한다. DB와 파일 저장소의 역할을 나누는 것은 흔히 쓰는 선택이다.

## 버킷, 객체, 경로

Supabase Storage는 파일을 객체로 관리한다. 버킷은 파일들을 묶는 단위이며 접근 방식이나 크기 제한 등을 설정한다. 객체 경로는 버킷 안에서 파일을 구분하는 이름이다.

```text
버킷: study-images
객체 경로: profiles/member-1/avatar.png
```

위 예시에서 `profiles/member-1/avatar.png`는 객체를 식별하는 경로다. `/`로 구분된 모습은 폴더와 비슷하지만 로컬 컴퓨터의 폴더 구조와는 다르다.

메타데이터는 파일 크기나 형식처럼 파일에 관한 정보다. `Content-Type: image/png`는 파일이 PNG 이미지 형식이라는 뜻이다. 이를 MIME 타입이라고도 부른다. 전달받은 형식 이름과 실제 파일 내용이 일치하는지는 별도로 확인해야 한다.

## 저장 경로와 다운로드 주소

저장 경로는 객체를 찾는 식별자이고 URL은 HTTP로 접근할 주소다. 경로만 안다고 모든 파일을 내려받을 수 있는 것은 아니다. 버킷의 공개 여부와 접근 권한을 함께 확인한다.

공개 버킷은 파일 제공 주소를 아는 사람이 파일을 읽을 수 있다. 비공개 버킷은 인증이나 별도 접근 수단이 필요하다. 서명 URL은 정해진 시간 동안 접근을 허용하는 주소다. 만료 전에는 주소 자체가 접근 수단이 될 수 있으므로 공유 범위를 주의한다.

## 업로드를 처리할 때

업로드는 파일을 저장소에 보내는 일, 다운로드는 저장소에서 파일을 받는 일이다. 업로드를 처리하는 기능은 파일 크기·형식과 사용자의 권한을 확인한다. 같은 경로에 다시 저장할 때 덮어쓸지도 정해야 한다.

파일 저장과 DB 기록은 보통 별도의 요청이다. 파일은 저장했는데 DB 기록이 실패하면 사용하지 않는 파일이 남을 수 있다. DB 트랜잭션 하나가 외부 Storage 요청까지 자동으로 취소해 주지는 않는다. 기능을 구현할 때 실패한 작업의 정리나 재시도 방법을 함께 정한다.

## 우리 프로젝트에서는

백엔드의 [SupabaseFileStorage](../../../backend/app/storage/supabase.py)가 파일 바이트를 저장한다. 기존 Supabase 클라이언트를 사용하고 저장 대상 버킷은 미리 준비한다.

업로드할 때는 비어 있지 않은 바이트인지와 크기 제한, 전달한 MIME 형식을 검사한다. 원본 파일명 대신 UUID로 새 객체 경로를 만들고 덮어쓰기를 금지한다. UUID는 식별자를 만드는 형식이다.

업로드에 성공하면 버킷과 객체 경로를 반환한다. 그림일기 이미지의 업로드는 [DiaryImageStorage](../../../backend/app/storage/diary_images.py)가 맡으며 실제 이미지 형식과 크기·픽셀 수를 확인한 뒤 공통 저장 모듈을 호출한다.

비공개 이미지를 읽을 때는 `SupabaseFileStorage`의 `signed_image`가 만료 시간이 있는 서명 URL을 만든다. 사용자 권한 확인과 업무 데이터 연결은 이 모듈을 호출하는 기능이 담당한다.

호출 규격과 검증 범위는 [Supabase Storage 파일 저장 모듈](../../engineering/file-storage.md)에 정리되어 있다.
